## 2. 整體架構：五層與一條規則

### 2.1 五層

```
┌──────────────────────────────────────────────────────────┐
│ 5. 瀏覽器      index.html + style.css + app.js           │  使用者看到與操作的東西
├──────────────────────────────────────────────────────────┤
│ 4. Cloudflare  https 加密、對外網址、單次請求上限 100 MB  │  不在你的電腦上
├──────────────────────────────────────────────────────────┤
│ 3. waitress    run.py：接收連線、分派給執行緒            │  只聽 127.0.0.1
├──────────────────────────────────────────────────────────┤
│ 2. Flask app   __init__.py、views.py、errors.py          │  決定每個網址做什麼
├──────────────────────────────────────────────────────────┤
│ 1. 儲存層      storage.py → uploads/ 資料夾              │  唯一碰硬碟的地方
└──────────────────────────────────────────────────────────┘
```

每一層只跟相鄰的層講話。瀏覽器不知道檔案放在哪個資料夾，儲存層也不知道什麼是 HTTP。

### 2.2 每個檔案的職責

| 檔案 | 職責 | 一句話 |
| --- | --- | --- |
| `run.bat` | 啟動捷徑 | 用專案自己的 Python 執行 `run.py` |
| `run.py` | 啟動 | 讀設定、檢查連接埠、把 app 交給 waitress |
| `app/config.py` | 設定 | 把 `.env` 的文字變成檢查過的 `Config` 物件 |
| `app/__init__.py` | 組裝 | `create_app()` 把所有零件接在一起 |
| `app/storage.py` | 儲存 | 房間 ID、檔名、讀寫刪、過期清理 |
| `app/views.py` | 路由 | 六個網址各自做什麼 |
| `app/errors.py` | 錯誤與 log | 404、403、413、CSRF、500 的處理 |
| `app/messages.py` | 文字 | 所有給使用者看的中文訊息 |
| `app/templates/index.html` | 頁面結構 | 擁有者頁與分享頁共用 |
| `app/static/style.css` | 外觀 | 版面、顏色、縮放 |
| `app/static/app.js` | 互動 | 上傳、彈窗、複製、flash |
| `tests/` | 測試 | 97 項自動檢查 |

### 2.3 一條規則：只有 `storage.py` 碰硬碟

整個專案最重要的設計決定是：**路由不可以自己組合檔案路徑**。`views.py` 裡找不到任何 `os.path.join` 或 `open()`，所有檔案操作都呼叫 `storage.py`。

理由是安全。網址裡的 `room_id` 和 `filename` 是外面的人可以隨便填的。如果有十個地方各自把它們接成路徑，就有十個地方可能漏掉檢查。集中在一個函式（`Storage._path`）裡，就只需要把那一個函式寫對、測對。

這個想法有個名字叫「單一咽喉點」（choke point），第 5 章會細看它。

### 自己試試看

1. 在 `app/views.py` 裡搜尋 `open(` 與 `Path(`，確認真的一個都沒有。
2. 在 `app/storage.py` 裡搜尋 `self._path(`，數一數有幾個地方呼叫它。

## 3. 通訊架構：一個請求的旅程

### 3.1 從手機到你的硬碟

假設有人用手機打開你的分享連結。這個請求經過的路：

```
手機瀏覽器
   │  https://你的網域/share_view/k3x9m2p7qa        （加密）
   ▼
Cloudflare
   │  解開 https，改用一般 http 轉送，
   │  並加上一行標頭：X-Forwarded-Proto: https
   ▼
你的電腦 127.0.0.1:5000  ←  waitress 在這裡聽
   │
   ▼
ProxyFix  →  Flask 路由  →  storage.py  →  uploads/k3x9m2p7qa/
```

這裡有三個設計值得理解。

**為什麼 waitress 只聽 `127.0.0.1`？** `127.0.0.1` 是「這台電腦自己」的位址，區網裡其他裝置和外面的網際網路都連不到它。能連進來的只有同一台電腦上的程式，也就是 Cloudflare 的連線程式。這樣你的網站對外只有 Cloudflare 一個入口。

**為什麼需要 `ProxyFix`？** Cloudflare 和 waitress 之間走的是 http，所以 Flask 以為自己是個 http 網站。如果不處理，`url_for(..., _external=True)` 產生的分享連結會是 `http://`，QR code 也跟著錯。Cloudflare 會在請求上附一行 `X-Forwarded-Proto: https`，告訴後面的程式「使用者原本是用 https 來的」。`app/__init__.py` 裡這一行讓 Flask 相信它：

```python
app.wsgi_app = ProxyFix(app.wsgi_app, x_proto=1)
```

`x_proto=1` 的意思是「只信任最靠近我的那一層代理」。

**一個實測才發現的坑。** waitress 預設會把 `X-Forwarded-*` 這類標頭刪掉（它不知道前面有沒有可信的代理），於是 `ProxyFix` 什麼都收不到。所以 `run.py` 啟動時多了一個參數：

```python
serve(app, ..., clear_untrusted_proxy_headers=False)
```

這個問題在自動測試裡抓不到，因為測試不經過 waitress。是實際把伺服器跑起來、送出帶標頭的請求才發現的。這是一個值得記住的教訓：**測試通過不等於系統正確，兩個零件各自正確，接起來仍可能出錯。**

### 3.2 伺服器怎麼認得你：session cookie

網站沒有帳號密碼，卻知道哪個房間是你的。靠的是 cookie。

第一次打開 `/` 時，`views.py` 的 `owner_room()` 做這件事：

```python
room_id = session.get("room_id")
if not storage.is_valid_room_id(room_id):
    room_id = storage.new_room_id()
    session["room_id"] = room_id
session.permanent = True
```

Flask 會把 `session` 的內容放進一個 cookie 送回瀏覽器。之後瀏覽器每次請求都會帶著它。

關於 Flask 的 session cookie，有兩個很多人誤會的地方：

- **它有簽章，但沒有加密。** cookie 的內容任何人都能解開來讀（只是 base64 編碼）。簽章的作用是防止竄改：內容被改過，簽章就對不上，Flask 會把它當成空的。
- **簽章用的就是 `SECRET_KEY`。** 這是 `SECRET_KEY` 必填、而且不能外流的原因。拿到它的人可以偽造任何房間的擁有者 cookie。

這也解釋了一個細節：`owner_room()` 會檢查 session 裡的 ID 格式。第二輪把房間 ID 從 32 碼改成 10 碼之後，舊瀏覽器的 cookie 裡還存著 32 碼的 ID。格式不合就當作沒有房間、重新發一個，而不是報錯。

cookie 的三個屬性設在 `app/__init__.py`：

| 設定 | 作用 |
| --- | --- |
| `HttpOnly` | 網頁裡的 JavaScript 讀不到這個 cookie，惡意腳本偷不走 |
| `SameSite=Lax` | 別的網站發起的 POST 不會帶上這個 cookie |
| `Secure`（由 `.env` 控制） | 只在 https 連線送出；本機用 http 測試時要關掉，否則 cookie 送不出去 |

### 3.3 六個網址

| 網址 | 方法 | 誰可以用 | 做什麼 |
| --- | --- | --- | --- |
| `/` | GET | 有 cookie 的人 | 擁有者頁面 |
| `/upload` | POST | 有 cookie 的人 | 上傳到自己的房間 |
| `/share_view/<room_id>` | GET | 任何人 | 唯讀分享頁 |
| `/qrcode/<room_id>` | GET | 任何人 | 分享連結的 QR code 圖片 |
| `/download/<room_id>/<filename>` | GET | 任何人 | 下載 |
| `/remove/<room_id>/<filename>` | POST | 房間的擁有者 | 刪除 |

**GET 與 POST 的分工**是這張表的重點。GET 只「看」，POST 才「改」。瀏覽器、搜尋引擎爬蟲、連結預覽程式都會自動發 GET，如果刪除做成 GET，一個預覽連結的聊天軟體就能把檔案刪掉。所以刪除按鈕是表單裡的 `<button>`，而不是一個連結。

知道房間 ID 的人就能看清單與下載，這是設計上的選擇：房間 ID 本身就是「鑰匙」。上傳與刪除則需要擁有者的 cookie。

### 3.4 流程一：第一次打開首頁

```
瀏覽器                                伺服器
  │ ── GET / ─────────────────────────▶ │
  │                                     │ session 裡沒有 room_id
  │                                     │ → 產生 k3x9m2p7qa，存進 session
  │                                     │ → 不建立資料夾
  │ ◀── 200 HTML + Set-Cookie ───────── │
  │ ── GET /static/style.css ─────────▶ │
  │ ── GET /static/app.js ────────────▶ │
  │ ── GET /qrcode/k3x9m2p7qa ────────▶ │  （分享彈窗裡的圖片）
```

注意「不建立資料夾」。網路上有大量自動程式到處掃網址，如果每次有人打開首頁就建一個資料夾，硬碟上會堆滿空房間。資料夾要等到第一次上傳才建立。

### 3.5 流程二：上傳三個檔案

這是全站最複雜的流程，分成前端與後端兩半。

```
app.js                                 伺服器
  │ 使用者拖進 a.txt、b.zip（太大）、c.png
  │
  │ a.txt：大小沒問題
  │ ── POST /upload ──────────────────▶ │ 檢查 CSRF token
  │    標頭 X-Requested-With: fetch     │ save_file() 寫入硬碟
  │ ◀── 200 {"category":"success",…} ── │
  │
  │ b.zip：超過上限 → 前端直接略過，不送出
  │
  │ c.png：大小沒問題
  │ ── POST /upload ──────────────────▶ │
  │ ◀── 200 {"category":"success",…} ── │
  │
  │ ── GET / ─────────────────────────▶ │
  │ ◀── 200 HTML ────────────────────── │
  │ 只取出檔案清單那一段，換掉畫面上的清單
  │ 顯示三則訊息：a 成功、b 略過、c 成功
```

三個決定：

**一個檔案一次請求。** Cloudflare 的 100 MB 上限與 Flask 的 `MAX_CONTENT_LENGTH` 都是針對「單次請求」。把三個 40 MB 的檔案放進同一個請求就是 120 MB，會整個被擋掉。分開送，每個檔案各自計算。

**JS 請求回 JSON，一般表單回轉址。** `views.py` 用一個標頭分辨兩種情況：

```python
def wants_json():
    return request.headers.get("X-Requested-With") == "fetch"
```

有這個標頭就回 `{"category": ..., "message": ...}`；沒有就 `flash()` 後轉址回首頁。後者讓沒有 JavaScript 的瀏覽器也能用。

**不重新載入整頁。** 全部傳完後，`refreshFileList()` 用 `fetch` 取回首頁的 HTML，只挑出檔案清單那一塊換上去。如果直接重新整理，JS 手上那幾則上傳結果就不見了。

### 3.6 流程三：刪除檔案（POST → 轉址 → GET）

```
瀏覽器                                伺服器
  │ ── POST /remove/k3x…/a1b2c3d4_a.txt ▶ │ 檢查 CSRF、檢查 session 的房間
  │                                       │ 刪除檔案
  │                                       │ flash("檔案已刪除")
  │ ◀── 302 Location: / ───────────────── │
  │ ── GET / ───────────────────────────▶ │ 取出 flash，放進頁面
  │ ◀── 200 HTML ──────────────────────── │
```

這個模式叫 **PRG（Post / Redirect / Get）**。如果 POST 直接回一個頁面，使用者按重新整理時，瀏覽器會問「要重新送出表單嗎？」，按下去就重複執行一次。回一個轉址，重新整理時重送的只是無害的 GET。

**flash 是什麼？** 轉址之後是一個全新的請求，上一個請求想說的話要有地方放。`flash()` 把訊息存進 session，下一個頁面用 `get_flashed_messages()` 取出並清掉。所以 flash 訊息只會顯示一次。

### 3.7 CSRF：為什麼表單裡藏著一串亂碼

設想你登入著 Quick Share，同時開了一個惡意網頁。那個網頁可以藏一個表單，目標指向你的 `/remove/...`，然後自動送出。瀏覽器會盡責地帶上你的 cookie，伺服器看到的是一個「有擁有者 cookie 的刪除請求」。這叫**跨站請求偽造（CSRF）**。

防法是在表單裡放一個只有你的頁面才知道的 token：

```html
<input type="hidden" name="csrf_token" value="{{ csrf_token() }}">
```

惡意網頁讀不到你的頁面內容，所以填不出正確的 token。`CSRFProtect` 會自動檢查每一個 POST。token 不對時，`errors.py` 顯示「頁面已過期，請重新操作」。

`SameSite=Lax` 已經擋掉大部分這類攻擊，CSRF token 是第二道防線。安全設計裡常見這種重疊的做法，稱為縱深防禦。

### 自己試試看

1. 啟動網站，按 F12 打開開發者工具的「Network」分頁，重新整理首頁，找出 3.4 圖裡的每一個請求。
2. 在「Application」分頁找到名為 `session` 的 cookie，看它的 `HttpOnly` 與 `SameSite` 欄位。
3. 拖兩個檔案上傳，在 Network 分頁確認真的是兩個獨立的 `upload` 請求，並點開看回應的 JSON。
4. 在開發者工具的 Elements 分頁，把某個刪除表單裡的 `csrf_token` 值改掉一個字再按刪除，看會發生什麼。

## 4. 本地設定：從 `.env` 到啟動

### 4.1 啟動時發生的事

```
雙擊 run.bat
   │  cd /d "%~dp0"                    切到 run.bat 所在的資料夾
   │  .venv\Scripts\python.exe run.py  用專案自己的 Python
   ▼
run.py  main()
   │  load_config()        讀 .env → 檢查 → Config 物件      失敗 → 印出中文錯誤，結束
   │  port_in_use()        連接埠有人在用嗎？                 有 → 印出中文錯誤，結束
   │  create_app(config)   組裝 Flask app，執行一次過期清理
   │  serve(app, …)        waitress 開始接收連線
```

### 4.2 虛擬環境（`.venv`）

`.venv` 是一個放在專案資料夾裡的獨立 Python 環境。這個專案需要的套件裝在裡面，不會和電腦上其他 Python 專案互相影響。`run.bat` 直接指定 `.venv\Scripts\python.exe`，所以不需要先「啟用」虛擬環境。

`requirements.txt` 把每個套件釘在確切版本（例如 `Flask==3.1.3`）。這樣半年後在另一台電腦重裝，拿到的是一模一樣的組合。

| 套件 | 用途 |
| --- | --- |
| Flask | 網站框架：路由、模板、session |
| waitress | 正式用的伺服器（Flask 內建的伺服器只適合開發） |
| python-dotenv | 讀 `.env` 檔 |
| qrcode、pillow | 產生 QR code 圖片 |
| Flask-WTF | 只用它的 CSRF 保護 |
| pytest（開發用） | 執行測試 |

### 4.3 `.env`：設定為什麼不寫在程式裡

`.env` 是一個純文字檔，一行一個設定。它被列在 `.gitignore` 裡，不會進版本控制。

這樣做有兩個理由。第一，`SECRET_KEY` 是密碼等級的東西，寫進程式就等於跟著程式碼到處流傳。第二，同一份程式可以在不同環境用不同設定，不需要改程式。

`.env.example` 是範本，列出所有變數與說明，`SECRET_KEY` 留空。它會進版本控制，讓拿到專案的人知道該設定什麼。

| 變數 | 預設 | 改了會影響什麼 |
| --- | --- | --- |
| `SECRET_KEY` | 必填 | 簽 cookie 用。**換掉它，所有人的擁有者身分都會失效** |
| `MAX_UPLOAD_MB` | 100 | 單檔上限。經 Cloudflare 時不要超過 100 |
| `MAX_FILES_PER_ROOM` | 10 | 每個房間留幾個檔案 |
| `ROOM_TTL_DAYS` | 30 | 房間多久沒新上傳就刪除 |
| `OWNER_SESSION_DAYS` | 30 | 擁有者 cookie 的有效天數 |
| `DISPLAY_NAME_LIMIT` | 12 | 長檔名前後各顯示幾個字 |
| `UPLOAD_DIR` | `uploads` | 檔案放哪裡 |
| `LOG_FILE` | `logs/quickshare.log` | log 放哪裡 |
| `HOST` / `PORT` / `THREADS` | `127.0.0.1` / `5000` / `4` | waitress 的參數 |
| `SESSION_COOKIE_SECURE` | `false` | 正式經 https 對外時設為 `true` |

### 4.4 `config.py`：把文字變成可信的值

`.env` 裡所有東西都是文字。`"100"` 要變成數字 `100`，`"true"` 要變成布林值。`config.py` 做三件事：轉型、補預設值、檢查。

```python
def _int(env, name, default):
    raw = env.get(name, "").strip()
    if raw == "":
        return default
    try:
        value = int(raw)
    except ValueError:
        raise ConfigError(f"設定 {name} 必須是整數，目前的值是「{raw}」") from None
    if value < 1:
        raise ConfigError(f"設定 {name} 必須大於或等於 1，目前的值是 {value}")
    return value
```

這裡的原則是**及早失敗、講清楚**。`MAX_UPLOAD_MB=abc` 這種錯誤如果不在啟動時擋下，會變成某個使用者上傳時才冒出來的神祕 500 錯誤。在啟動時就停下來，並說出是哪個變數、目前是什麼值，你三秒鐘就能修好。

另一個細節是路徑：

```python
PROJECT_ROOT = Path(__file__).resolve().parent.parent
```

`__file__` 是 `config.py` 自己的位置，往上兩層就是專案根目錄。相對路徑（例如 `uploads`）一律以這裡為基準，而不是「目前工作目錄」。這樣不管你從哪個資料夾、用什麼方式啟動，檔案都會放在同一個地方。

### 4.5 `create_app(config)`：application factory

`app/__init__.py` 沒有在檔案最外層直接建立 app，而是提供一個函式 `create_app(config)`，呼叫它才建立。

好處在測試時最明顯。`tests/conftest.py` 這樣用：

```python
Config(
    secret_key="test-secret",
    max_upload_mb=1,
    max_files_per_room=3,
    upload_dir=tmp_path / "uploads",
    log_file=tmp_path / "logs" / "test.log",
    start_cleanup_thread=False,
)
```

每個測試拿到一個全新的 app，檔案放在暫存資料夾，上限改成 1 MB、3 個檔案（測試「超過上限」時就不必真的產生 100 MB 的檔案），背景清理執行緒關掉。測試完全碰不到你真正的 `uploads/`。

### 4.6 `run.py` 的連接埠檢查

```python
def port_in_use(host, port):
    with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as sock:
        sock.settimeout(1)

```

一般來說，兩個程式搶同一個連接埠時，後來的會啟動失敗。但 waitress 在 Windows 上不會報錯，兩個程式會同時掛在同一個埠，請求可能被舊的那個接走。開發時就真的遇到：新版啟動了，瀏覽器看到的卻是舊版的頁面。

## 5. 儲存層：唯一碰硬碟的地方

### 5.1 硬碟上長什麼樣子

```
uploads/
├─ k3x9m2p7qa/                      ← 房間 ID 就是資料夾名稱
│  ├─ 9f1c2a7b_報告.pdf              ← <8 碼 uid>_<安全檔名>
│  ├─ 03de88f1_報告.pdf              ← 同名檔案可以並存，uid 不同
│  └─ 5b7a90c2.part                  ← 正在上傳中的暫存檔
└─ 7hw2n0c4zt/
   └─ c41e06aa_photo.jpg
```

沒有資料庫。「這個房間有哪些檔案」就是「這個資料夾裡有哪些檔案」，「檔案什麼時候上傳的」就是檔案的修改時間。資料越少的地方，越不會出現兩邊對不上的問題。

### 5.2 房間 ID：10 碼小寫英數

```python
ROOM_ID_ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyz"

def new_room_id():
    return "".join(secrets.choice(ROOM_ID_ALPHABET) for _ in range(ROOM_ID_LENGTH))
```

三個決定：

**用 `secrets`，不用 `random`。** `random` 產生的數字看起來亂，但可以從前幾個結果推算出後面的。`secrets` 使用作業系統提供的亂數來源，專門用在密碼、token 這類不能被猜到的東西上。

**只用小寫。** Windows 的檔案系統不分大小寫，`AbC` 和 `abc` 是同一個資料夾。如果 ID 混用大小寫，兩個不同的 ID 可能指向同一個房間，一個人就看得到另一個人的檔案。

**10 碼夠不夠？** 房間 ID 是分享連結唯一的保護，所以要算一下有多少種可能：

| 字元集 | 10 碼的組合數 | 相當於 |
| --- | --- | --- |
| 小寫 hex（16 種字元） | 16¹⁰ ≈ 1.1 × 10¹² | 40 bits |
| 小寫英數（36 種字元） | 36¹⁰ ≈ 3.7 × 10¹⁵ | 約 52 bits |

同樣 10 碼，小寫英數比 hex 多了約 3300 倍的組合。這就是第二輪你要求「降到 10 位」時，我把字元集從 hex 換成英數的原因：網址一樣短，但難猜得多。

（訂正：我在第二輪回報時說「約四千倍」，正確的數字是 36¹⁰ ÷ 16¹⁰ = 2.25¹⁰ ≈ 3325，約三千三百倍。）

要誠實說的是，這比初版的 32 碼 hex（128 bits）弱很多。對個人用的檔案快傳，52 bits 配上 30 天自動過期是合理的取捨；如果要放機密文件，就不該只靠網址保密。

### 5.3 檔名：不信任使用者給的任何東西

上傳的檔名是使用者的瀏覽器送來的字串，可以是任何內容。`safe_filename()` 分七步把它洗乾淨：

| 步驟 | 做什麼 | 例子 |
| --- | --- | --- |
| 1 | 用 `/` 和 `\` 切開，只留最後一段 | `..\..\secret.txt` → `secret.txt` |
| 2 | Unicode 正規化（NFC） | 同一個字的兩種編碼方式統一成一種 |
| 3 | 空白換成 `_` | `我的 報告.pdf` → `我的_報告.pdf` |
| 4 | 只留中文、英數、`.`、`_`、`-` | `a<b>:c?.txt` → `abc.txt` |
| 5 | 去掉頭尾的 `.` | `.htaccess` → `htaccess` |
| 6 | 超過 150 字就截斷主檔名，保留副檔名 | `很長…很長.pdf` → `很長….pdf` |
| 7 | 結果是空的就拒絕 | `???` → 拋出 `InvalidFilename` |

這是**白名單**的做法：列出允許的字元，其他一律丟掉。相反的做法是黑名單（列出危險字元再移除），但你永遠列不完。Windows 的保留字元、控制字元、看起來像斜線的 Unicode 字元，黑名單總會漏。

步驟 1 同時處理 `/` 和 `\` 是因為這是 Windows。在 Linux 上 `\` 只是一個普通字元，在 Windows 上它是路徑分隔符。

存檔時會在前面加上 8 碼隨機的 uid，所以同名檔案上傳兩次不會互相覆蓋。顯示與下載時用 `display_name()` 去掉前綴，使用者看到的仍是原本的檔名。

### 5.4 `_path()`：單一咽喉點

所有讀、寫、刪都先經過這個函式，拿到路徑後才動手：

```python
def _path(self, room_id, name=None, allow_temp=False):
    check_room_id(room_id)                                    # ① 格式
    room_dir = (self.upload_dir / room_id).resolve()
    if not room_dir.is_relative_to(self.upload_dir.resolve()):  # ② 位置
        raise InvalidRoomId(room_id)
    ...
    if not (STORED_NAME_RE.fullmatch(name) or ...):           # ① 格式
        raise InvalidFilename(name)
    path = (room_dir / name).resolve()
    if not path.is_relative_to(room_dir) or path == room_dir: # ② 位置
        raise InvalidFilename(name)
    return path
```

它做兩層檢查：

- **① 格式檢查**：房間 ID 必須符合 `^[0-9a-z]{10}$`，檔名必須符合 `^[0-9a-f]{8}_[中文英數._-]+$`。這兩個樣式裡根本沒有 `/`、`\`、`..` 的位置，所以 `../../.env` 這種東西在第一層就被擋掉。
- **② 位置檢查**：`resolve()` 把路徑算成絕對路徑（會展開 `..` 與捷徑），再用 `is_relative_to()` 確認結果確實在房間資料夾裡面。

既然第一層已經擋掉了，為什麼還要第二層？因為第一層依賴「我的正規表示式沒寫錯」這個假設。第二層不管字串長什麼樣，只問最終結果落在哪裡。兩層用不同的方法檢查同一件事，一層出錯時另一層還在。

這就是路徑穿越（path traversal）攻擊的防法。攻擊的樣子是在網址裡塞 `..%5C..%5C.env`（`%5C` 是 `\` 的編碼），想讓伺服器把專案根目錄的 `.env` 當成檔案送出來。

### 5.5 `save_file()`：寫到一半斷線怎麼辦

```python
uid = secrets.token_hex(4)
temp_path  = self._path(room_id, f"{uid}.part", allow_temp=True)
final_path = self._path(room_id, f"{uid}_{safe}")
try:
    written = 0
    with open(temp_path, "wb") as out:
        while chunk := upload.stream.read(CHUNK_SIZE):
            written += len(chunk)
            if written > self.max_bytes:
                raise FileTooLarge(upload.filename)
            out.write(chunk)
    os.replace(temp_path, final_path)
except BaseException:
    temp_path.unlink(missing_ok=True)
    raise
```

四個值得學的寫法：

**先寫暫存檔，完成後才改名。** 如果直接寫到正式檔名，上傳到一半時別人打開分享頁，會看到並下載到一個不完整的檔案。寫到 `.part`，完成後用 `os.replace()` 改名。改名在檔案系統上是一瞬間完成的動作，別人看到的要嘛是沒有這個檔案，要嘛是完整的檔案。`list_files()` 會忽略不符合正式檔名格式的東西，所以 `.part` 檔不會出現在清單裡。

**一塊一塊讀。** 每次讀 1 MB 寫 1 MB，而不是把整個檔案讀進記憶體。四個人同時傳 100 MB，也只占用幾 MB 的記憶體。

**邊寫邊數大小。** `MAX_CONTENT_LENGTH` 已經在外層擋了一次，但它多留了 1 MB 給表單的其他部分，所以這裡精確地再檢查一次檔案本體。

**失敗時清理，然後把例外往外丟。** `except BaseException` 之後有 `raise`。它不是要吞掉錯誤，而是要在離開前刪掉暫存檔，再讓錯誤繼續往外傳。寫 `except: pass` 把錯誤藏起來，是最難除錯的一種寫法。

### 5.6 配額與一個時間的小陷阱

存檔成功後，`_enforce_quota()` 把清單排序（新到舊），刪掉第 N 個之後的檔案。

排序靠的是檔案的修改時間，這裡有個陷阱：連續快速上傳兩個檔案，它們的修改時間可能完全相同，排序就不確定誰新誰舊，配額可能刪錯檔案。所以存檔後多了這幾行：

```python
newest = existing[0]["mtime_ns"] if existing else 0
new_time = max(time.time_ns(), newest + 10_000_000)
os.utime(final_path, ns=(new_time, new_time))
```

新檔案的時間至少比房間裡目前最新的檔案晚 10 毫秒。這個問題在多檔上傳加入後更容易發生，而它是在寫測試時發現的。

### 5.7 過期清理

`purge_expired_rooms()` 掃描 `uploads/`，對每個**名稱符合房間 ID 格式**的資料夾，找出裡面最新檔案的修改時間，超過 `ROOM_TTL_DAYS` 就整個刪除。

「名稱符合格式才處理」是刻意的保守。`shutil.rmtree()` 會刪掉整個資料夾，如果你哪天在 `uploads/` 裡放了一個叫 `backup` 的資料夾，或者 `UPLOAD_DIR` 不小心設成別的地方，這個函式不會碰任何它不認得的東西。會刪資料的程式，範圍要畫得越窄越好。

順帶一提：初版留下的 32 碼舊房間資料夾，現在不符合 10 碼的格式，所以清理不會碰它們。如果你的 `uploads/` 裡有這種資料夾，需要手動刪除。

執行時機在 `app/__init__.py`：啟動時一次，之後由一個背景執行緒每小時一次。

```python
def run_cleanup(store):
    try:
        store.purge_expired_rooms()
    except Exception:
        logger.exception("過期清理失敗")
```

這裡的 `except` 沒有 `raise`，和 5.5 相反。原因是背景執行緒裡沒接住的例外會讓執行緒結束，之後就再也不清理了，而且沒有人會發現。所以這裡接住它、寫進 log、下個小時再試。該不該吞掉例外，取決於「往外丟之後誰會處理」。

## 6. 路由與錯誤處理

### 6.1 `views.py`：薄薄的一層

路由函式都很短，因為真正的工作在 `storage.py`。以下載為例：

```python
@bp.get("/download/<room_id>/<filename>")
def download(room_id, filename):
    require_valid_room(room_id)
    path = get_storage().get_file(room_id, filename)
    if path is None:
        flash(messages.FILE_NOT_FOUND, "warning")
        return redirect(url_for("main.share_view", room_id=room_id))
    response = send_file(path, as_attachment=True, download_name=storage.display_name(filename))
    response.headers["X-Content-Type-Options"] = "nosniff"
    return response
```

一行一行看：

- `require_valid_room`：房間 ID 格式不對就回 404。
- `get_file`：檔名格式不對或檔案不存在都回傳 `None`。路由不需要知道是哪一種。
- `as_attachment=True`：告訴瀏覽器「下載它」，而不是「打開它」。
- `nosniff`：禁止瀏覽器猜測檔案類型。

後兩項一起防一種攻擊：有人上傳一個內容是惡意網頁的檔案，再把下載連結傳給別人。如果瀏覽器直接把它當網頁打開，裡面的腳本就會以你的網站的身分執行。強制下載加上禁止猜測類型，檔案就只是檔案。

### 6.2 權限檢查

刪除的第一行：

```python
if session.get("room_id") != room_id or not storage.is_valid_room_id(room_id):
    abort(403)
```

網址裡的 `room_id` 是任何人都能填的，cookie 裡的 `room_id` 有簽章保護、偽造不了。兩者相同才代表「你是這個房間的擁有者」。

上傳則完全不看網址，直接用 cookie 裡的房間（`owner_room()`），所以根本沒有「上傳到別人房間」的可能。

### 6.3 `errors.py`：出錯時使用者看到什麼

| 狀況 | 使用者看到 | log 寫什麼 |
| --- | --- | --- |
| 404 找不到 | 簡短的錯誤頁與回首頁連結 | 一行 WARNING，含路徑，不寫 traceback |
| 403 沒有權限 | 同上 | 一行 WARNING |
| 413 檔案太大 | 「檔案太大了！上傳限制為 N MB」 | 不寫 |
| CSRF 驗證失敗 | 「頁面已過期，請重新操作」 | 不寫 |
| 500 程式出錯 | 「伺服器發生錯誤，請稍後再試」 | 完整的 traceback |

這張表背後的原則是：**使用者只需要知道該怎麼辦，開發者才需要知道發生了什麼。** 把 traceback 顯示給使用者既沒有幫助，還會洩漏檔案路徑與程式結構。

404 不寫 traceback 是因為它太常見了。公開的網站每天會收到大量亂掃網址的請求，每個都寫一大段，真正的錯誤會被淹沒。

log 用 `RotatingFileHandler`，單檔 1 MB，保留 3 份舊檔。寫滿就換檔，最舊的自動刪除，不會把硬碟塞滿。

### 6.4 `messages.py`：文字集中在一處

所有給使用者看的中文都在這個檔案。想把「檔案已刪除」改成「已刪除檔案」，只改一個地方，不用在路由、模板、JavaScript 裡到處找。

連 JavaScript 要用的文字也放在這裡，例如：

```python
UPLOAD_PROGRESS = "上傳中… {done}/{total}"
```

模板把它放進 HTML 的 `data-progress-text` 屬性，`app.js` 讀出來，再把 `{done}`、`{total}` 換成數字。所以 `app.js` 裡沒有任何中文字串，也沒有寫死的數字。第 7.2 節會再看到這個手法。

## 7. 前端：模板、樣式、行為

前端三個檔案各管一件事：HTML 管「有什麼」，CSS 管「長什麼樣」，JavaScript 管「會做什麼」。

### 7.1 `index.html`：一個模板，兩種頁面

擁有者頁與分享頁共用同一個模板，用一個變數切換：

```html
{% if is_owner %}
  <h1 class="title">Quick Share</h1>
  ...上傳區、Share file 按鈕...
{% else %}
  <h1 class="title">Share Files</h1>
  ...回首頁連結...
{% endif %}
```

`{% ... %}` 與 `{{ ... }}` 是 Jinja 模板語法，在**伺服器上**執行。瀏覽器收到的是已經填好的純 HTML。這表示分享頁的 HTML 裡根本沒有上傳表單與刪除按鈕，而不是「有，但用 CSS 藏起來」。藏起來的東西使用者可以從開發者工具叫出來，不存在的東西則不行。當然，真正的防線還是在後端的權限檢查。

**自動跳脫。** `{{ file.display_name }}` 輸出時，Jinja 會把 `<` 變成 `&lt;` 這類的替換。即使有人設法讓檔名裡出現 `<script>`，它也只會被當成文字顯示，不會被執行。這個保護是預設開啟的，只有加上 `|safe` 才會關掉，所以專案裡一個 `|safe` 都沒有。

**過濾器。** `{{ file.size | filesize }}` 把位元組數變成 `1.2 MB`，`{{ name | shorten }}` 把長檔名的中間換成 `...`。這兩個函式寫在 `storage.py`，在 `create_app()` 裡註冊成 Jinja 過濾器。完整檔名另外放在 `title` 屬性，滑鼠停在上面就看得到。

**巨集。** 兩個彈窗的 × 按鈕長得一樣，所以寫成一個巨集 `close_button()`，用兩次。

### 7.2 後端怎麼把數值交給 JavaScript

```html
<form class="upload-form js-upload-form" ...
      data-max-bytes="{{ max_upload_bytes }}"
      data-skipped-message="{{ skipped_message }}"
      data-progress-text="{{ msg.UPLOAD_PROGRESS }}">
```

```javascript
const maxBytes = Number(form.dataset.maxBytes);
```

`data-*` 屬性是 HTML 提供的「隨便你放資料」的地方，JavaScript 用 `dataset` 讀取（`data-max-bytes` 變成 `dataset.maxBytes`）。

這樣上限的數字只存在於一個地方（`.env`），經過 `config.py` → `views.py` → 模板 → JavaScript 一路傳下來。把 `.env` 的 100 改成 50，前端的檢查、說明彈窗的文字、後端的限制全部一起變。

### 7.3 `js-` 開頭的 class

模板裡有兩種 class：

```html
<label class="upload-zone js-upload-zone">
```

`upload-zone` 給 CSS 用，`js-upload-zone` 給 JavaScript 用。分開的好處是，改外觀時重新命名 CSS 的 class 不會弄壞 JavaScript，反過來也一樣。看到 `js-` 就知道「有程式在找這個元素，不要隨便刪」。

### 7.4 `style.css`：版面

樣式表只用 class 選擇器，一個檔案，沒有 `@import`。

面板是一個置中的直欄：

```css
.panel {
  width: 100%;
  max-width: calc(320 * var(--u) + 32px);
  margin: 0 auto;
  display: flex;
  flex-direction: column;
  row-gap: calc(15 * var(--u));
}
```

- `width: 100%` 加 `max-width`：螢幕窄時填滿，寬時不超過上限。這一組取代了舊版固定的 `width: 320px`。
- `margin: 0 auto`：左右邊距自動平分，也就是水平置中。
- `display: flex; flex-direction: column`：裡面的東西由上往下排，`row-gap` 是它們之間的間距。

檔案清單有 `min-height`，所以沒有檔案時那塊空間還在，「尚無檔案」幾個字不會緊貼著按鈕。

圖示是深色的 PNG，用 `filter: invert(0.45)` 調成灰色。同一張圖可以用不同的數值調出不同深淺，不需要準備多張圖。

### 7.5 `--u`：一個變數放大整個介面

第三輪你說電腦上的介面太小。最直接的做法是寫一段「螢幕寬於某個值時，把每個尺寸都改大」，但那樣要把幾十個數字各寫兩次，而且只有大小兩段，中間沒有過渡。

實際的做法是定義一個單位：

```css
.page {
  --u: clamp(1px, 0.7px + 0.05vw, 1.5px);
}
```

然後所有尺寸都寫成它的倍數：

```css
.title { font-size: calc(24 * var(--u)); }
.icon  { width: calc(20 * var(--u)); }
```

`--u` 就是「放大後的 1px」。它是 1px 時一切是原尺寸，是 1.5px 時一切放大 1.5 倍。

`clamp(最小, 理想, 最大)` 的意思是：盡量用中間的值，但不低於最小、不高於最大。中間的 `0.7px + 0.05vw` 裡，`vw` 是視窗寬度的 1%。代入幾個寬度算算看：

| 視窗寬度 | `0.05vw` | `0.7px + 0.05vw` | 實際的 `--u` |
| --- | --- | --- | --- |
| 375px（手機） | 0.19px | 0.89px | 1px（被最小值擋住） |
| 600px | 0.30px | 1.00px | 1px |
| 1280px | 0.64px | 1.34px | 1.34px |
| 1600px | 0.80px | 1.50px | 1.5px |
| 1920px | 0.96px | 1.66px | 1.5px（被最大值擋住） |

0.7 和 0.05 這兩個數字是解聯立方程式得來的：要在 600px 時剛好是 1、1600px 時剛好是 1.5。斜率是 (1.5 − 1) ÷ (1600 − 600) = 0.0005px/px，也就是 `0.05vw`；再代回去得到截距 0.7。

結果是手機維持原樣，600px 到 1600px 之間平滑地變大，超過 1600px 就停在 1.5 倍。在 1280px 的螢幕上，面板寬約 429px、標題約 32px；在 1920px 上是 480px 與 36px。

不跟著縮放的只有兩樣：手機兩側的 16px 邊距，以及 1px 的細框線。QR code 加了 `image-rendering: pixelated`，放大後方塊的邊緣仍然銳利。

### 7.6 flash 訊息：浮在上面，不佔位置

```css
.flash-list {
  position: fixed;
  top: calc(70 * var(--u));
  left: 50%;
  transform: translateX(-50%);
  width: min(calc(100% - 32px), calc(320 * var(--u)));
  pointer-events: none;
}
```

一般的元素排在「文件流」裡，一個接一個往下排，多一個元素，後面的全部往下移。`position: fixed` 把元素從文件流裡拿出來，釘在視窗的固定位置。所以訊息出現或消失時，上傳區與清單的位置完全不變。

- `left: 50%` 加 `translateX(-50%)`：先把左邊緣放到畫面正中間，再往左移回自己寬度的一半，結果是水平置中。這是置中 fixed 元素的標準寫法。
- `top: calc(70 * var(--u))`：放在標題列下方，不會蓋住標題與說明圖示。
- `pointer-events: none`：這個容器本身不攔截滑鼠，訊息之間的空隙點得穿。每一則訊息再各自設回 `auto`，所以訊息本身可以點擊關閉。

代價是訊息出現時會暫時蓋住上傳區的上半部。

另外有兩段特殊情況的規則：

```css
@media (prefers-reduced-motion: reduce) { ... }
@media (scripting: none) { ... }
```

第一段是尊重使用者的系統設定。有些人會因為畫面動態感到不適，在作業系統裡開了「減少動態效果」，這時訊息不滑動，只做很短的淡出。第二段是沒有 JavaScript 時，訊息無法自動消失，所以改回排在面板裡，免得一直擋住內容。

### 7.7 `app.js`：四個功能

頁面載入後執行四個設定函式：

```javascript
document.addEventListener("DOMContentLoaded", function () {
  setupFlashes();
  setupUpload();
  setupDialogs();
  setupCopy();
});
```

所有事件都用 `addEventListener` 綁定，HTML 裡沒有 `onclick="..."`。行為全部集中在 `app.js`，想知道「按這個按鈕會發生什麼」只需要看一個檔案。

#### 上傳

點擊選檔與拖曳是兩個入口，但走同一個函式 `uploadFiles()`。主要的迴圈：

```javascript
for (let i = 0; i < files.length; i++) {
  const file = files[i];
  text.textContent = fill(form.dataset.progressText, { done: i + 1, total: files.length });
  if (file.size > maxBytes) {
    results.push({ category: "warning", message: ... });
    continue;
  }
  results.push(await sendOne(form, file));
}
```

`await` 是這段的關鍵字。`sendOne()` 發出網路請求，需要時間。`await` 的意思是「等這個做完再往下」，所以檔案是一個接一個上傳，而不是同時全部送出。

前端先檢查大小是為了體驗：不用等 100 MB 傳完才被伺服器拒絕。但它不是安全措施，前端的檢查任何人都能繞過，所以後端仍然檢查兩次（第 5.5 節）。**前端檢查是為了使用者方便，後端檢查才是真正的規則。**

`uploading` 這個變數是一把鎖：上傳進行中再拖檔案進來，`uploadFiles()` 第一行就直接返回。

#### 拖曳的兩個細節

瀏覽器對「把檔案拖進網頁」的預設反應是直接打開那個檔案，整個頁面被換掉。所以 `dragover` 與 `drop` 都要呼叫 `event.preventDefault()` 取消預設行為。上傳區有一組，`window` 上還有一組，後者處理「沒拖準、放在上傳區外面」的情況。

第二個細節是 `dragDepth` 這個計數器。滑鼠拖著檔案從上傳區移到裡面的圖示上時，瀏覽器會先對圖示發 `dragenter`，再對上傳區發 `dragleave`，儘管滑鼠根本沒離開上傳區。如果收到 `dragleave` 就移除提示樣式，邊框會閃個不停。所以進入時加一、離開時減一，數到零才真的移除。

#### 更新清單

```javascript
const response = await fetch(window.location.pathname, ...);
const page = new DOMParser().parseFromString(await response.text(), "text/html");
const newList = page.querySelector(".js-file-list");
list.replaceChildren(...);
```

取回首頁的 HTML，用 `DOMParser` 解析成一份不顯示的文件，從裡面挑出檔案清單，換掉畫面上的那一塊。

這個做法的好處是清單的 HTML 只有一份來源，就是 Jinja 模板。另一種做法是讓後端回傳 JSON、由 JavaScript 自己組出每一列，但那樣同一個清單就有兩套產生方式，改版面時要改兩個地方。

#### 彈窗

用的是 HTML 內建的 `<dialog>` 元素。`dialog.showModal()` 打開它，瀏覽器會自動處理：蓋上半透明背景、把鍵盤焦點鎖在彈窗裡、按 Esc 關閉。這些以前都要自己寫。

點背景關閉是自己加的：

```javascript
dialog.addEventListener("click", function (event) {
  if (event.target === dialog) {
    dialog.close();
  }
});
```

`event.target` 是實際被點到的元素。點在彈窗的內容上，target 是裡面的按鈕或圖片；點在外面的背景上，target 才是 `dialog` 本身。

#### 複製連結

你在第二輪回報手機上複製不了。新的寫法依序嘗試三種方式：

```
1. navigator.clipboard.writeText()       新式 API，只在 https 下可用
        │ 不可用或失敗
        ▼
2. 選取文字 + document.execCommand("copy")   舊式做法，支援較廣
        │ 也失敗
        ▼
3. 選取文字，顯示「請長按連結手動複製」
```

舊的寫法只有第一步，失敗時只默默選取文字，使用者看不到任何反應。新的寫法保證每一次按下都有回饋。

選取文字時多了一行 `setSelectionRange(0, input.value.length)`，因為 iOS 上對唯讀輸入框呼叫 `select()` 常常沒有作用。

你當時遇到的原因我沒有確認。最可能的是當時的環境不提供剪貼簿功能（非 https 的網址，或 LINE 這類 App 的內建瀏覽器）。

這種寫法叫**漸進增強**：先用最好的方法，不行就退一步，每一步都確保使用者不會卡住。

#### flash 的佇列

```javascript
const MAX_VISIBLE_FLASHES = 4;
const flashQueue = [];
```

訊息先放進佇列，畫面上同時最多顯示 4 則。一則消失後，佇列裡的下一則才出現，並從頭計算自己的停留時間。一次上傳 10 個檔案時，不會有 10 則訊息蓋滿螢幕，也不會有訊息還沒輪到就過期。

停留時間：

```javascript
function flashDuration(item) {
  const base = item.classList.contains("flash-success") ? 4000 : 8000;
  return Math.max(base, 1500 + item.textContent.length * 120);
}
```

成功 4 秒，警告與錯誤 8 秒，因為後者需要你讀懂原因。訊息很長時（例如長檔名）按字數再延長。

伺服器渲染出來的 flash（例如「檔案已刪除」）在頁面載入時被 `setupFlashes()` 收進同一個佇列，所以兩種來源的訊息行為一致。

程式裡有一行註解說明了一個被放棄的功能：原本做了「滑鼠停在訊息上就暫停倒數」，但點掉一則之後，下一則會補到游標底下，於是一直暫停、永遠不消失。實測發現後就拿掉了。

## 8. 測試：怎麼知道它是對的

### 8.1 執行

```
.venv\Scripts\python.exe -m pytest
```

目前是 97 項，全部通過，約一秒跑完。`tests/test_storage.py` 直接測儲存層的函式，`tests/test_routes.py` 用 Flask 的測試客戶端假裝成瀏覽器發請求。

### 8.2 一個測試長什麼樣子

以「配額」為例，概念上是：

```python
def test_quota(client, config):
    for i in range(5):                 # 準備：上傳 5 個檔案（測試設定的上限是 3）
        upload(client, f"f{i}.txt")
    html = client.get("/").get_data(as_text=True)
    assert "f4.txt" in html            # 驗證：最新的還在
    assert "f0.txt" not in html        # 驗證：最舊的被刪了
```

三段式：準備狀態、執行動作、檢查結果。`client` 與 `config` 是 `conftest.py` 提供的「夾具」（fixture），pytest 會自動建立並傳進來。每個測試都拿到全新的 app 與空的暫存資料夾，測試之間互不影響。

### 8.3 測了哪些事

| 類別 | 確認的事 |
| --- | --- |
| 檔名清理 | 中文保留、空白轉底線、路徑成分被去除、全非法字元被拒絕、過長時截斷 |
| 路徑穿越 | 各種含 `..`、`\`、`%5C`、`%2F` 的網址都被拒絕，而且房間外預先放的檔案還在 |
| 上傳與清單 | 上傳後出現在兩種頁面、同名檔案並存 |
| 配額 | 超過上限只留最新的；只是打開清單不會刪任何東西 |
| 權限 | 別人的 cookie 刪不了你的檔案；分享頁沒有上傳表單與刪除按鈕 |
| CSRF | 沒有 token 的上傳與刪除被拒絕；用 GET 呼叫刪除得到 405 |
| 太大 | 超過上限得到警告，而且沒留下檔案或暫存檔 |
| 過期清理 | 31 天前的房間被刪除，未過期的與名稱不符的資料夾不受影響 |
| 延遲建立 | 只打開首頁不會產生資料夾 |
| 設定 | 缺 `SECRET_KEY` 或數值不合法時，錯誤訊息含變數名稱 |
| 房間 ID | 新 ID 是 10 碼；cookie 裡的舊格式 ID 會被換發 |
| JSON 上傳 | 帶 `X-Requested-With` 時回 JSON，而且不留下 flash |

注意路徑穿越那一列的後半句：「房間外預先放的檔案還在」。只檢查「回應是 404」不夠，因為程式可能一邊回 404 一邊已經把檔案刪了。好的測試檢查的是你真正在乎的結果。

### 8.4 測試做不到的事

自動測試不經過 waitress、不經過 Cloudflare、也沒有真的瀏覽器。所以開發時另外做了兩種驗證：

- **真實伺服器**：實際啟動 waitress，用 HTTP 請求走完整個流程。3.1 節的代理標頭問題與 4.6 節的連接埠問題，都是在這一步才發現的。
- **真實瀏覽器**：用程式操控 Edge，在 375、768、1280、1920px 四種寬度下檢查版面、量座標、截圖。

三種驗證各自抓得到不同的錯誤，少一種就有一類問題看不見。

## 9. 安全性總整理

把前面各章提到的防護收在一張表，方便對照：

| 威脅 | 防護 | 位置 | 章節 |
| --- | --- | --- | --- |
| 用 `..` 讀取或刪除房間外的檔案 | 格式白名單，加上 `resolve()` 後檢查位置 | `storage.py` 的 `_path()` | 5.4 |
| 惡意檔名 | 七步清理，白名單字元 | `storage.py` 的 `safe_filename()` | 5.3 |
| 別的網站偷偷替你送出刪除請求 | CSRF token，加上 `SameSite=Lax` | `__init__.py`、模板 | 3.7 |
| 偽造擁有者身分 | cookie 有 `SECRET_KEY` 簽章 | Flask session | 3.2 |
| 網頁腳本偷走 cookie | `HttpOnly` | `__init__.py` | 3.2 |
| 刪除別人房間的檔案 | 比對 session 與網址裡的房間 ID | `views.py` 的 `remove()` | 6.2 |
| 檔名或內容被當成網頁執行 | Jinja 自動跳脫；下載強制為附件並加 `nosniff` | 模板、`views.py` | 6.1、7.1 |
| 超大檔案塞滿硬碟 | `MAX_CONTENT_LENGTH`，加上寫入時逐塊計數 | `__init__.py`、`storage.py` | 5.5 |
| 爬蟲製造大量空資料夾 | 第一次上傳才建立資料夾 | `views.py` 的 `owner_room()` | 3.4 |
| 猜到別人的房間 ID | 10 碼小寫英數，約 52 bits，用 `secrets` 產生 | `storage.py` | 5.2 |
| 繞過 Cloudflare 直接連進來 | waitress 只聽 `127.0.0.1` | `.env` 的 `HOST` | 3.1 |
| 錯誤訊息洩漏內部資訊 | 使用者只看到簡短訊息，細節寫進 log | `errors.py` | 6.3 |
| 清理程式誤刪其他資料 | 只處理名稱符合房間 ID 格式的資料夾 | `storage.py` 的 `purge_expired_rooms()` | 5.7 |

貫穿這張表的三個想法：

1. **外面來的資料一律不信任。** 網址、檔名、表單欄位、cookie，都先檢查再使用。
2. **用白名單，不用黑名單。** 列出允許的，其他全部拒絕。
3. **重要的檢查做兩層。** 路徑有格式與位置兩層，大小有請求與檔案本體兩層，跨站請求有 `SameSite` 與 token 兩層。

## 10. 目前的限制與還沒驗證的事

### 設計上的限制

- **知道連結就能下載。** 沒有密碼保護，房間 ID 就是鑰匙。不適合放機密檔案。
- **擁有者身分綁在瀏覽器上。** 清除 cookie 或換一台裝置，就失去那個房間的上傳與刪除權限。檔案還在，連結也還能用，30 天後自動清除。
- **上傳進度只到「第幾個檔案」。** 單一大檔案傳到百分之幾，目前不顯示。
- **flash 訊息會暫時蓋住上傳區上半部。** 這是「不佔版面」的代價。

### 還沒有人驗證過的事

以下項目只在電腦上的 Edge 以模擬方式檢查過，需要你實際操作一次：

- 真實手機上的複製按鈕，特別是 iPhone 的 Safari，以及 LINE 等 App 的內建瀏覽器。
- 真實手機上浮動訊息的外觀與點擊關閉。
- 用滑鼠從檔案總管實際拖檔案進上傳區（開發時是用程式模擬拖曳事件）。
- Firefox 與 Safari 上的版面。
- 桌面放大 1.5 倍這個幅度，你主觀上覺得剛好、太大還是不夠。

### 上線前要記得

- `.env` 裡的 `SESSION_COOKIE_SECURE` 改成 `true`。
- `SECRET_KEY` 用自己產生的值，而且不要換。換掉它，所有人的擁有者 cookie 都會失效。
- 如果 `uploads/` 裡有初版留下的 32 碼舊資料夾，手動刪除。
